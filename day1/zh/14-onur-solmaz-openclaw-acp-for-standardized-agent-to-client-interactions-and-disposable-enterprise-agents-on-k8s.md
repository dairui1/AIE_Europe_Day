欢迎。这个演讲是关于在 OpenClaw 上构建 ACP（Agent 客户端协议），也涉及其他内容，比如如何将开源 Agent、开源 Agent 框架部署到 Kubernetes 上。我希望今天能以一种好的方式分享我过去两个月所做的工作。先简单介绍一下我自己。在 ChatGPT 问世前几个月，我就开始构建 Agent 运行框架（harness）了。我在 OG Codex 模型（即 Davinci Code 2）上构建了一个 JupyterLab 扩展。随着时间推移，最初的编程框架在不断演变，就像忒修斯之船一样，被拆解再重建了无数次。我目前在一家初创公司担任创始工程师，在行业里工作了三年半到四年。我从 Cloudbot 刚出现在 Discord 上时就开始使用 OpenClaw 了。我一直关注 Peter，从他写"Claude Code 就是我的电脑"那篇文章开始——我当时心想："这家伙疯了吧，我可不会把自己的机器交给它。"但他勇往直前，为我们开辟了道路。当我在 Discord 看到 Cloudbot 时，我惊呆了。第二天我就在公司的集群里安装了它，它基本上在 Discord 上与大家交流，所有人都和我一样震惊了。我们已经做了几年的企业级销售，所以我开始添加了一个 MS Teams 集成，以备将来可能用到，之后便成为了维护者。它被改名两次时我都在场。今天，我的关注重点是 Agent 的互操作性与编排。我的目标之一是加速 OpenClaw 及周边软件的企业采用，同时解决 OpenClaw 的安全问题——Peter 之前已经谈了很多，这是正在推进的工作，我没有更多要补充的。

我一开始就直接着手开发工作流。我创建了一个 PR，把它称为"Discord 驱动开发"。不过叫"Telegram 驱动开发（TDD）"更贴切，因为缩写正好是 TDD。之后我把它用到了个人场景，发现 OPUS 对复杂任务并不那么可靠——那时候是这样，现在已经好多了，Agent 也在不断进步。但 Codex 是我的主要框架，我想在 Discord 里使用 Codex，但它很基础——我在玩"传话游戏"，让 Opus 告诉 Codex 去做某件事。天知道它说了什么，因为提示词的措辞非常关键，但不知为何还是能运行。我会去查看 Codex 会话，它大致转述了我的意思，但我知道这可以做得更简便。今天，我在 Discord 上运行着完整的 IDE，同时处理并行工作负载——在任意时刻有一到五个频道在运作，与一到五个 Agent 同时工作。你可以看到 Codex 一到五，还有一个用于测试 OpenClaw ACP 功能的。这是我某些频道的样子，对于随时随地编码来说非常好用——我是个热衷于副业项目的人，AI 让这类并行工作变得轻松得多，有了灵感就能在周末执行和发布。

ACPX 就是这样诞生的，我是通过 Discord 构建的。你把 Discord 频道通过 ACP 绑定到 Codex，也可以使用 Codex App Server Protocol，由另一位维护者 Herald 开发。这里有我在飞往伦敦前使用它的例子——将 ACP 文档转换成 PDF，但我必须说"放到 temp 目录"，因为 OpenClaw 不了解这个 harness，无法发送给我，所以我再去另一个频道让它发过来。我们是开发者，工具不一定精致，但我们清楚其利弊。

什么是 ACP？大多数人会问，它像 MCP 吗？MCP 是用来给模型提供工具的，ACP 用于标准化 Agent 与客户端的交互。向 Zed 致敬——我忘了放 Zed 的 Logo。Zed 正在用 Rust 开发一款新编辑器，效率更高，内存占用更少，不是 Electron。我从去年秋天开始使用 Zed。如果你在 VS Code 或 Claude Code 上使用 Codex，各方都在构建不同的插件，存在大量重复工作。如果能将它们统一在一个接口下，只需构建一次就能发布，这就是 ACP 的核心理念，也大幅减少了重复工作。目前还有竞争性标准：Agent Protocol 用于 Agent 之间的通信，ACP（Agent Client Protocol）用于人与 Agent 之间的交互，但 Agent 也可以通过后者与其他 Agent 通信。长远来看，随着这些协议的采用，我们将支持所有协议。我选择 ACP 是因为当我最需要 Codex 和 Claude Code 适配器时，只有 Zed 构建了它们，Google 当时还没有，所以我选择了它。

在向 OpenClaw 添加功能时，需要通过 CLI 操作。于是我想，创建一个 ACP 的 CLI，让任何 Agent 都能通过命令行调用其他 Agent。这就是 ACPX 的起点，慢慢演变成 ACP 的瑞士军刀。

在 OpenClaw，我们有"消防水管"——总共超过 60,000 个 PR，平均每天有 300 到 500 个处于打开状态，基本上一夜之间人们都表示对 OpenClaw 感兴趣。我们有数以万计的利益相关方想要添加功能，项目目前最大的挑战是如何吸收所有人的需求，如何在不产生 AI 垃圾的前提下构建出优雅的系统来满足各方需求。Peter 的工作流给了我灵感——当 PR 提交过来时，你先问你的 Claude："这是什么？"大多数时候描述都是 AI 生成的，你需要问它是什么，是否是最佳修复方案，然后与 Agent 反复讨论。原因是大家遇到 OpenClaw 的问题后直接用 GitHub 说"请修复"，然后就发来了一堆垃圾，你无法合并但也不能直接丢弃，这是来自用户的关键反馈，需要分类归档。Vincent 也提到了这一点。

所以我开始以抽象的方式创建工作流：PR 进来后，找出意图、评判实现、检查冲突和 CI 是否通过。我构建了一个工作流，包括"评审-重构"循环——我相信，只要不让 Agent 设计新东西，而是让它发现可轻松修复的浅层 bug，就不会产生垃圾。在我创建的抽象工作流中，可以让它做表面重构，或者在需要根本性重构时转交给人工，解决冲突也不需要手动操作了。我们实质上是在为 Agent 创建标准操作程序（SOP）——这是一个 Agent 工作流引擎，驱动一个 Codex 会话。这就是 ACPX，它是一个通用工作流引擎，可以用于其他场景。

你需要将 Agent 慷慨地应用于问题，把自己从循环中抽离，用 Agent 来解决它。个人 Agent 和企业 Agent 处于一个光谱的两端——在工作中你会消耗更多的推理资源，这意味着企业级别有更多商业价值可挖掘，这也是我对企业 Agent 和 OpenClaw 潜力感到兴奋的原因。

关于按需一次性 Agent：如果你在 Slack、Teams 或 Discord 上使用 OpenClaw，这是一个实例。问题是你无法轻松与多个实例交互——你需要创建新的 Slack 应用、新的名称、新的头像，还需要编写 app manifest，而且这些平台还不支持多 Agent 批量创建。屏幕上展示了我让 ChatGPT 生成的构想：Agent 的名称可以由底层应用生成，你可以分别与它们交互。在这一愿景被支持之前，我在另一个 UI 上使用它，因为我们都将开始为每个任务启动一个 Agent，它们会工作、创建和编辑文件，并保持同步。要实现这一点，你需要几个关键组件：Kubernetes、Agent 框架（OpenClaw 或 Codex 可以是其中之一）、ACP 或 GitHub（赋予读写权限），以及类似 Dropbox 使用的算法进行状态数据同步。

有一些项目正在承担这个工作，这是我在日常工作中做的事情——一个开源 Go 运算器，处理复杂部分。比如你想在 Slack 上创建一个礼宾 Agent，与之对话，但因为公司有 100 名员工，会遇到瓶颈，就可能需要创建新的 Agent，它会给你一个网页链接。代码库是 TextCortex spritz，我来演示一下我们的使用场景——用于错误报告。在 Slack 上，你可以让它派出一个 Agent 来调试，询问某次发布后是否有新 bug，然后让它创建一个 Agent。如果我能把那个 Agent 放到 Slack 里，我会的，但目前还不行，所以放在另一个 UI 里。这是一个开源项目，UI 是一个 React 应用，托管在你部署这些 Helm charts 的集群中。它会在那里启动一个对话，开始处理问题。这类似于 Codex Web 或 Devon，但实际上使用了完整的 Kubernetes pod——消耗资源多，但我认为是更好的抽象，因为 OpenClaw 已经证明，给 Agent 一台完整的计算机，效果会强大得多。

如果你对在内部部署并在上面使用 Codex感兴趣，我可以帮你搭建。如果你有一个每天接收数百个 Issue 的开源项目，我可以帮你处理。这个项目处理了 Slack 周边的所有连接工作，保持这些 Agent 在线，以及用户体验，而底层通过 ACP 实现 Agent 无锁定——你可以切换 Agent，一切都是抽象的。好了，这就是我的演讲，感谢收听。这里有我的社交链接。需要说明的是，最后一部分关于我在 TextCortex 的工作内容——感谢收听。
