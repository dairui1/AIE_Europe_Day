Victor 是大家或许已经有所耳闻的 AI 员工，它正在迅速走红。我们在今年二月发布了它，当时对增长毫无预期，只是一次实验，结果出乎所有人意料——立即实现了产品市场契合，在全球范围内获得了大规模采用，我们都追不上这个速度了。

那么 Victor 是什么？Victor 是一名 AI 员工。当你想到 AI 员工时，应该把它想象成一名普通员工：它生活在你生活的地方，生活在 Slack 里，没有独立的网页应用。就像你的团队成员一样，你不需要去单独的地方来调用它。它参与你的讨论，在话题（threads）和频道（channels）中，并且它能访问你能访问的工具。它接入了 3,000 个集成。如果它没有你的某个集成，它可以自己构建连接。本质上，Victor 能使用你公司使用的任何工具，因此 Victor 拥有你所有工具的上下文。与人类员工不同，Victor 拥有对整个公司横向而广泛的上下文。举个例子，你现在聘请一位 CMO，如果这位 CMO 能访问你的代码库并为其做出贡献，效果会好得多。Victor 可以做到。它为公司各个领域带来了那种近乎博士级别的全面理解。

让我们从 Victor 和公司的故事讲起。早在 2023 年，我们从最初的使命就是打造 AI 员工。那时候是在 ChatGPT 发布之后，我们认为打造 AI 员工的正确方式是通过浏览器。那时候没有工具调用，没有很棒的代码生成模型，所以通过浏览器执行操作大概是正确的方向——浏览器是非常通用的界面，几乎可以用它使用任何工具，大多数应用都有可以交互的网页版。那时它叫 JCAI，工作方式是：对你的 DOM 进行快照，以无损方式压缩，然后根据这个快照和你的目标决定下一步——是在 Google 搜索栏输入内容，还是点击登录按钮。这在理论上应该是可行的，而且确实可行，但在当时模型能力的限制下，大概只能可靠地完成三到五步，而所谓"可靠"是以 60% 的成功率来衡量的，每一步都在叠加误差。即便如此，JCAI 当时在最流行的 agentic 基准测试 WebArena 上仍是最先进的 Web Agent，但很难做成有用的产品，因为可靠性和速度问题。现在直接调用几个工具或函数就能立即得到输出，而 Web Agent 要等一分钟才能失败，相当困难。不过 Web Agent 非常了不起，如今已经比过去好用多了。

之后 JCAI 变成了一个邮件 Agent。Claude Sonnet 3.5 出来了，我们构建了第一个 Agent 循环，真正想要实现的体验是：你不用去网页应用请求 Agent 做事，而是 Agent 拥有所有必要的上下文，能主动为你提出任务。我们用 Jace 实现了这一点，它是一个很棒的产品，也有很好的产品市场契合，现在依然在运行，你们应该去体验一下。它的工作方式是：每当有邮件进来，就会触发一个 Agent 循环，连接到你的工具，不仅仅是起草邮件回复，还能进行工具操作——比如有人申请退款，Agent 可以自动处理，当然也可以设置人工审批门控。

今年二月我们发布了 Victor。大家都知道 OpenClaw 是个人 Agent，我们一直想打造的是公司级别的 Agent，即公司 Agent。首先要问的是：公司 Agent 与个人 Agent 有什么区别？我们认为：公司 Agent 应该住在你住的地方、在你工作的地方工作，并且拥有所有公司上下文。对于个人 Agent，公司里的每个人都要单独连接自己的集成，各自运行。而公司 Agent 不同——只需公司里的一个人连接某个集成，Victor 就会继承这个集成的权限（当然可以调整），整个团队就都能使用了，不需要连接 100 次。如我所说，3,000 个工具，生活在 Slack，能跨部门处理任何事情。

这带来了挑战，我主要讲一个：从个人 Agent 到团队 Agent，从一个用户到多个用户，内存（memory）是个大问题。OpenClaw 曾经担心内存随时间积累而混乱，这是合理的顾虑——但想象一下，相同的架构和记忆，面对的是 100 个用户而不是 1 个，内存可能以 100 倍的速度耗尽，是个大挑战，我们已经解决了。

另一个挑战是 Slack 有不同的频道，公司也有不同的层级结构，我们需要遵守，而且人们经常给 Agent 下达相互冲突的指令。设想 Victor 在成长频道、工程频道以及用户私信中都存在。Victor 会从成长频道或高管频道获取上下文，但必须确保这些上下文不会泄露到工程或支持频道。同样，如果用户私信 Victor 谈论自己的问题，Victor 不应该引用成长频道的上下文，除非这个用户来自成长团队。这大大增加了访问结构的复杂性。

我们选择 Slack 作为界面——我认为这就是公司级 AGI。原因有两个，但先说 Slack 会带来什么问题。选择 Slack 有两个主要原因：第一，我们希望 Victor 感觉像真人员工，而你与真人员工的互动是在 Slack 里，就像与你的队友一样；第二，Victor 是一个功能强大的 Agent，需要执行复杂任务，这些任务不会立即完成，可能需要 10 分钟。如果你打开网页应用让 Agent 做某件事，你切换了上下文，然后需要等 10 分钟，这很令人沮丧——你习惯了 ChatGPT 那种即时反馈，期望 30 秒搞定。但强大的 Agent 不是这样运作的。为什么 Slack 更好？因为如果你在 Slack 上 ping 某人说"帮我做个应用"然后 10 分钟后得到回复，你会惊讶——没有任何队友能在 10 分钟内给你做一个应用。所以感知是不同的，与你的日常 Slack 体验相比，延迟感其实很低。

但 Slack 中有一些问题。在网页应用中，你打开一个新的 Agent 或话题，与这个 Agent 对话，有清晰的单线程。但在 Slack 里有很多互动模式：私信（DM）、在公开频道和话题中参与、用表情符号回应、编辑消息等，所有这些都是 Agent 的输入，都需要以某种方式融入线性上下文中，而不是一个单一的话题。我们需要管理这一切。

举个例子：当有人删除一条消息，人类会认为任务不再需要继续；当有人编辑消息，也应该响应编辑。但假设你在私信一个同事（无论是 Victor 还是真人），在 Slack 里发起了一个 thread，然后忘记了那个 thread，直接开了一个新的 DM——人类有之前 thread 的上下文，但对 Agent 来说，这是一个全新的区域和任务。所以需要做的是，每当 Victor 收到私信时，查看之前的消息，以某种方式将它们滚入现有对话。这只是需要面对的挑战之一。

有趣的是，语气（tone）比我原以为的重要得多。我来分享一个来自我们某个客户的例子。我们现在用 Claude Opus 4.6 作为 Victor 的主模型，我们想试试 GPT-4.5 用于工具调用和代码生成，效果确实很好，价格也更便宜，理论上可以替换。但我们没有这样做，最有趣的原因是性格（personality）。不知为何，我们的用户——可能也与我们的架构有关——都非常喜欢 Opus，当我们做 AB 测试时大家都开始抱怨。我认为那个模型有某种美丽之处值得我们学习。Opus 在 Victor 里还有点"俏皮"，不确定是我们的团队还是谁让它变成这样的，但确实挺有意思，我鼓励大家试试。

主动性（proactivity）是 Victor 的强大功能之一：它可以主动建议可以自动化的工作流。比如你在成长团队讨论一个 AB 测试和结果，意识到某个选项表现很好，决定采用它。Victor 可以接入你的 PostHog 或任何分析工具，实际核查，如果你说的情况不成立，它会指出来。曾经发生过 Victor 查看了 PostHog 后说"你说的是真的，但这在统计上并不显著"，然后给出了计算说明。这很有趣，也是一个优势——如果 Victor 能加入对话并提供帮助，它会在工作区内得到更广泛的使用，对产品有好处。但如果 Victor 在第一天就开始这样做——这曾经发生过——安全团队会很抓狂，因为有人把 Victor 加进工作区后，Victor 就开始给所有人发私信和参与话题，安全部门就疯了。这就是为什么我认为应该先用少数几个用户赢得信任，然后再广泛推广。

关于共享上下文的价值，我时间不多了，简单说说 Victor 与 Claude Code 等 Agent 的区别。Claude Code 是在你桌面上运行的，所以有所不同。Victor 的优势是它在云端运行，不需要你的电脑开着。另一个优势是共享上下文——如我所说，对 Victor 来说，只需公司一个人连接一个集成，整个团队就都能使用。想象 100 人的团队，成长团队有 20 人，如果每个人都要单独连接 Meta Ads 集成，很痛苦。而且如果每个人都连接自己的集成，还可能有人连错，Victor 就会一头雾水，不知道该用哪个集成，大大增加用户负担。

我想强调的是：Victor 不是工具，它是一个"雇员"。我来说一个客户故事。美国最大的电商品牌之一，他们的团队管理员连接了 Victor，而第一个接入的集成是他自己的个人 Gmail。然后整个团队开始和 Victor 谈论这个人的私人邮件，这个人发消息给我说："兄弟，Victor 把我的数据都泄露出去了，你们在干什么？"我说："你为什么要把自己的私人邮件开放给 Victor？如果你雇了一个新员工，你会给他访问你私人邮件的权限吗？大概不会吧。"话虽如此，这给了我们很好的启发，我们由此为 Victor 添加了一个功能：可以对集成进行作用域限定，不是所有集成都会被共享；如果你想让自己的私人集成只在你私信 Victor 时可用，或者公开时也可用，现在也支持。

总结一下，一个优秀的 AI 协作伙伴需要什么？我认为有三大支柱，这是一个技术人群，我鼓励大家尝试打造自己的 Victor：第一，帮助完成工作，相对容易——如今模型的能力足够了，通过 Pipedream 的连接器集成也会很好用；第二，了解公司、掌握 Slack 的上下文，确保能充分利用这些上下文，你可能需要经历 Slack 审批流程，这可能繁琐；第三，让它友好，这很重要，要确保 Victor 喜欢你的团队，你的团队也喜欢 Victor。

这是我们对未来的愿景：每家公司都有 AI 员工，我认为这是不言而喻的。历史上，AGI 的愿景自 17 世纪就伴随着我们。微积分的发明者 Gottfried Leibniz 曾思考人类做不必要事情的问题，他想制造一台计算机，殊不知，计算只是我们能自动化的众多认知任务之一。我认为我们现在正处于历史上这样一个美好时刻——我们可以自动化所有认知任务，我们可以成为这场革命的一部分。让我读一下他的名言："优秀的人把时间花在计算的劳役上，实属不值。让我们把这些留给机器吧。"最后，我想请大家扫描这个二维码，点击注册，把 Victor 加入你的 Slack，测试一下。在场每个人都有 100 美元的免费额度，没有任何附加条件，随时可以移除 Victor，它一定会带来很大价值。如果没有，打电话给我，我会确保它做到。谢谢大家。
